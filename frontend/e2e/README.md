# Отчет по End-to-End тестированию

Проект: Telegram Wish Mini App  
Уровень тестирования: системное / End-to-End тестирование  
Инструмент запуска: Selenium WebDriver + Jest  
Окружение: frontend-приложение Svelte/Vite, backend API в Docker, mock только для Telegram и внешних сервисов.

## 1. Отчет о выполненной работе и использованных инструментах

В проекте реализован набор из 20 End-to-End сценариев, покрывающих основные бизнес-процессы приложения: регистрацию, профиль, настройки, шаринг профиля, анкету, желания и вишлисты. Тесты находятся в папке [frontend/e2e/selenium](./selenium) и разделены по функциональным модулям:

| Файл | Назначение |
| --- | --- |
| [registration.test.js](./selenium/registration.test.js) | Регистрация и первый запуск приложения |
| [profile.test.js](./selenium/profile.test.js) | Редактирование профиля |
| [settings.test.js](./selenium/settings.test.js) | Настройки приватности и интерфейса |
| [sharing.test.js](./selenium/sharing.test.js) | Поделиться профилем и публичный профиль |
| [questionnaire.test.js](./selenium/questionnaire.test.js) | Заполнение и валидация анкеты |
| [wishes.test.js](./selenium/wishes.test.js) | Создание и валидация желаний |
| [wishlists.test.js](./selenium/wishlists.test.js) | Создание вишлистов и действия с желаниями внутри них |

Для E2E-тестирования создано отдельное окружение, максимально приближенное к рабочему:

- frontend запускается через Vite;
- backend запускается как реальное FastAPI-приложение;
- база данных PostgreSQL запускается в Docker;
- запросы frontend к `/api/v1/...` идут в настоящий backend;
- mock используются только для Telegram WebApp, clipboard/share API браузера и внешней загрузки файлов в S3.

### Использованные инструменты

| Инструмент | Для чего используется | Почему выбран |
| --- | --- | --- |
| Selenium WebDriver | Управление реальным браузером Chrome | Соответствует требованию использовать инструмент UI/web-тестирования и позволяет проверять приложение глазами пользователя |
| ChromeDriver | Связка Selenium с Google Chrome | Позволяет запускать тесты в том же браузере, который используется пользователями |
| Jest | Запуск тестовых файлов, группировка сценариев и отчетность | Уже используется в проекте для тестов, поэтому не добавляет лишнюю тестовую инфраструктуру |
| Vite dev server | Запуск настоящего frontend-приложения | Позволяет тестировать реальные Svelte-экраны приложения, а не статичную HTML-заглушку |
| Docker Compose | Поднятие backend и PostgreSQL | Обеспечивает воспроизводимое окружение для системных тестов |
| PostgreSQL | Тестовая база данных | Используется настоящая СУБД, как часть рабочего окружения backend |

Скрипт запуска E2E-тестов описан в [frontend/package.json](../package.json):

```json
"test:e2e": "cross-env NODE_OPTIONS=--experimental-vm-modules jest --config e2e/jest.e2e.config.js --runInBand"
```

Файл [scenarioRunner.js](./selenium/scenarioRunner.js) отвечает за подготовку окружения: запуск backend, запуск Vite, создание Chrome WebDriver и очистку тестовых данных перед сценариями.

Фрагмент запуска backend-окружения:

```js
await runCommand('docker', [
  'compose',
  '-f',
  path.join(repoRoot, 'docker-compose.e2e.yaml'),
  'up',
  '-d',
  '--build',
  'database',
  'backend',
]);
```

Для изоляции сценариев используется специальный backend endpoint `POST /v1/e2e/reset`, доступный только в E2E-режиме. Он очищает тестовые данные и заново подготавливает фикстуры:

```js
await resetBackendData();
```

Backend endpoint находится в [backend/app/api/routers/e2e.py](../../backend/app/api/routers/e2e.py):

```python
@router.post("/reset")
async def reset_e2e_data(session: AsyncSession = Depends(get_session)):
    ensure_e2e_enabled()
    ...
```

Настоящие API-запросы frontend перенаправляются на backend через proxy в [frontend/vite.config.js](../vite.config.js):

```js
server: {
  proxy: {
    '/api': {
      target: process.env.E2E_API_BASE_URL || 'http://127.0.0.1:8000',
      changeOrigin: true,
      rewrite: (path) => path.replace(/^\/api/, ''),
    },
  },
}
```

Mock внешних сервисов подключается в [frontend/src/e2e/setup.js](../src/e2e/setup.js). Важно, что этот файл не подменяет backend API, а только имитирует Telegram WebApp и внешние браузерные/интеграционные сервисы:

```js
window.Telegram = {
  WebApp: {
    initData,
    initDataUnsafe: { user },
    ready: () => undefined,
    expand: () => undefined,
  },
};
```

Для загрузки файлов оставлен mock внешнего S3 endpoint, так как S3 является внешним сервисом и не относится к проверяемому backend API приложения:

```js
if (url.pathname.startsWith('/api/v1/s3/file/')) {
  return jsonResponse({ filename: `e2e-upload-${Date.now()}.png` });
}
```

## 3. Отчет о прохождении тестов на сервере непрерывной интеграции

Для запуска системных тестов в CI используется тот же сценарий, что и локально:

```powershell
cd frontend
npm run test:e2e
```

Перед запуском должен быть доступен Docker, так как E2E runner автоматически поднимает отдельное backend-окружение из [docker-compose.e2e.yaml](../../docker-compose.e2e.yaml):

```yaml
services:
  database:
    image: postgres:15
  backend:
    build:
      context: ./backend
    environment:
      E2E_MODE: 1
```

В CI или локальном runner тесты выполняются в headless-режиме Chrome. Для визуального запуска в Chrome можно отключить headless:

```powershell
cd frontend
$env:E2E_HEADLESS="0"
$env:E2E_PAUSE_MS="500"
npm run test:e2e
```

Контрольный прогон E2E-тестов:

| Параметр | Значение |
| --- | --- |
| Команда | `npm run test:e2e` |
| Окружение | ChromeDriver + Selenium WebDriver + Vite + FastAPI backend + PostgreSQL в Docker |
| Режим backend | `E2E_MODE=1` |
| API | Настоящие запросы к backend |
| Mock | Только Telegram WebApp, clipboard/share, внешний S3 upload |
| Test Suites | 7 passed, 7 total |
| Tests | 20 passed, 20 total |
| Snapshots | 0 total |
| Итог | Успешно |

Итоговый результат последнего прогона:

```text
Test Suites: 7 passed, 7 total
Tests:       20 passed, 20 total
Snapshots:   0 total
```

Таким образом, системное тестирование проверяет не изолированные компоненты, а основные пользовательские сценарии в рабочем окружении: браузер взаимодействует с настоящим frontend-приложением, frontend отправляет реальные HTTP-запросы в backend, backend работает с PostgreSQL, а внешние зависимости Telegram и S3 заменены управляемыми mock-объектами для воспроизводимости тестов.
